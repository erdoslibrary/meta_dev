# Real-to-Sim 공간 퍼즐 스튜디오 — 명세 v1.1

> Meta Global AI Developer Hackathon 출품작 · 브레인스토밍 결과 정리 (2026-11-03) · 코드 폴더 위치: `docs/spec.md`

## 1. 한 줄 정의

공간형 퍼즐을 설치하기 전에, 서로 다른 성향의 AI 에이전트들이 시뮬레이션 안에서 먼저 플레이해 보고 **퍼즐이 제작자의 머릿속에만 갇혀 있지 않은지(지식의 저주)** 를 검증하는 도구.

로봇에서 MuJoCo로 실물 전에 동작을 돌려 보듯, 공간 퍼즐에도 "만들기 전에 돌려 보는 단계"를 만든다.

## 3. 측정 대상과 범위

**측정하는 것**
- 퍼즐의 연결이 제작자 아닌 사람에게도 떠오르는가 (문제 난이도의 적절성)

**측정하지 않는 것**
- 장소 이동, 길찾기 (지시문으로 장소를 분명히 정의함. 쉬워져도 무방)
- 관찰력 (사물을 찾아내는 능력)

**이번 범위 밖 (Non-goals)**
- 실제 AR 인식 (원작은 리얼월드 스튜디오 AR로 기존 사물을 찍으면 NPC가 등장. 시뮬레이션에서는 찍기를 `view` 행동으로 표현하고, 찍은 사물이 맞는지는 엔진이 사물 id로 판정)
- 3D 복원 (MapAnything 등). 평면도로 충분
- 온라인 사람 테스트 수집. 사람 기준 데이터는 오프라인 기록을 사용
- 게임 모드 (플레이 중 고스트 표시)
- 30분 분량 전체 이식. 핵심 퍼즐만 이식

## 4. 전체 구조와 착수 순서

```
[1단] 공간 재연 ──▶ [재연 검증] ──▶ [에이전트 시뮬레이션] ──▶ [로그] ──▶ [보고서]
```

에이전트는 공간을 JSON으로 받고 이동을 측정하지 않으므로, 두 갈래를 나란히 진행한다.

| 갈래 | 내용 | 순서 |
|---|---|---|
| 갈래 1 (핵심) | 퍼즐 JSON → 에이전트 실행 → 로그 → 보고서 | 먼저 |
| 갈래 2 (보여 주기) | 평면도, 격자, 발자국 지도, 주문 연출 | 뒤에 합류 |

로그 형식을 먼저 확정하면 두 갈래가 서로를 기다리지 않는다. 지도가 덜 되어도 보고서가 있으면 결과물이 성립한다.

## 5. 1단: 공간 재연

### 5.1 평면도
- 창작자가 마우스로 공간 형태를 그림 (벽, 문)
- 그리기 배경으로 비상대피도 사진 사용 가능 (비율이 맞는 기준 1장)

### 5.2 축척
- 그린 문의 픽셀 폭을 **0.9m** 로 간주해 자동 계산. 창작자의 직접 측정 없음
- 대략 그린 문은 폭이 부정확할 수 있으므로 계산값은 초기값으로 쓴다. 격자를 겹쳐 본 뒤 바깥 사각형을 드래그해 칸 수를 고칠 수 있다
- 문이 여러 개면 평균, 배율 차이가 크면 경고

### 5.3 격자 좌표 (체스식)
- 열은 알파벳, 행은 숫자. **왼쪽 아래가 A1**. 26열 초과 시 AA, AB...
- **칸 크기 1m**
- 원점은 평면도 바깥 사각형의 왼쪽 아래
- 층이 여러 개면 접두어: `2F-C4`
- 같은 사물도 좌표로 구분: `desk@C4`, `desk@F2`
- 큰 사물이나 구역은 범위: `B3:D5`
- 방 이름은 선택 필드 `rooms`에 칸 범위와 함께 적는다. 지도에 층과 함께 표시하고 에이전트에게도 공개한다

### 5.4 사물
```json
{
  "id": "desk@C4",
  "label": "desk",
  "cells": "C4:D4",
  "description": "",
  "photos": ["desk_front.jpg", "desk_puzzle.jpg"],
  "state": "locked"
}
```
- 트리거: 같은 칸 또는 이웃 칸에 들어오면 찍을 수 있게(`view`) 됨. 찍으면 설명과 첫 번째 사진을 봄
- 모든 사물에 사진이 1장 이상 필요. 일부 사물에만 있으면 퍼즐 위치가 드러나기 때문. 첫 번째 사진은 퍼즐 표시가 없는 평소 모습으로 둠
- 사물 라벨과 칸 위치는 SAM 3.1(박스) + Muse Spark(이름, 대략적 크기)가 사진에서 제안하고 창작자가 배치
- 크기 추정 방식은 미결 (§12): SAM 박스 비율(같은 사진 속 문 기준) 또는 Muse 추정

### 5.5 퍼즐
- **선형 구조**: 1번을 풀면 다음 장소 지시를 받음
- 지시문에 좌표를 포함해도 됨 (예: "C4의 책상으로 가라")
- 퍼즐 정보: NPC, NPC 대화, 그림 이미지, 문제 텍스트, 정답 글자 수, 텍스트 힌트 1개
- 진행: 장소에 가서 현재 퍼즐의 사물을 찍으면(오프라인의 AR 반응) NPC가 등장해 대화를 보여 주고, 이어서 이미지 퍼즐이 제시된다
- 대화 속 단서는 힌트가 아니라 문제의 일부로 본다
- NPC 이미지는 캐릭터별로 제작하는 화면 연출용이며 에이전트 관측에는 넣지 않는다
- 오답과 정답 때의 NPC 반응 대사(`on_wrong`, `on_correct`)는 선택 필드로, 화면 연출 전용이며 에이전트 관측에는 넣지 않는다

### 5.6 사진에서 퍼즐 초안 (여유)
- 사진 1장에서 SAM과 Muse가 사물을 찾고, Muse가 그 사물로 퍼즐 초안을 만든다. 사물 사진을 퍼즐 그림으로 쓰므로 이미지 생성 모델은 필요 없다
- 제작자가 승인한 초안만 일반 퍼즐과 같은 검증과 실행을 거친다

## 6. 재연 검증

원칙: AI가 만든 결과를 **AI 밖의 코드로 검증**하고, 실패하면 이유를 돌려주어 다시 만들게 한다 (워크숍 구조).

### 6.1 자동 검사 (사물과 연결은 필수, 평면도와 축척은 여유)

마우스 평면도 빌더가 여유 항목이므로, 평면도와 축척, 사물의 방 안 위치와 크기 범위, 길 연결 검사도 여유 항목이다. 필수 범위는 `docs/acceptance.md`가 정한다.

| 대상 | 검사 |
|---|---|
| 평면도 | 벽이 닫혀 있는가, 문이 벽 위에 있는가 |
| 축척 | 문 폭 기준 배율끼리 크게 어긋나지 않는가 |
| 사물 | 방 안에 있는가, 서로 겹치지 않는가, 크기가 상식 범위인가 (책상 0.6~2m 등) |
| 트리거 | 모든 사물에 사진이 있는가 |
| 연결 | 지시문이 가리키는 사물이 지도에 있는가, 지시문에 그 사물의 칸 좌표나 방 이름이 있는가, 길이 있는가 |

### 6.2 오라클 실행 (필수)
- 모든 정답을 아는 가짜 플레이어가 1번부터 끝까지 진행
- 끝까지 가면 플레이 가능한 시뮬레이션. 막히면 퍼즐이 아니라 재연의 문제

### 6.3 내용 동일성
- 퍼즐 이미지, NPC 대화, 문제 텍스트, 글자 수, 힌트가 오프라인과 같은가
- 대화문에 정답이 그대로 들어 있지 않은가
- 사물 설명과 방 이름은 단서를 담아도 되며, 이 검사의 대상이 아니다. 오래 막히면 포기하는 사람이 많고 단서는 재미를 위한 요소이므로 엄격하게 막지 않는다

### 6.4 출력
- 재연 보고서: 통과 항목, 수정 항목, 창작자 확인 필요 항목
- 최종 보고서에 "재연 검증을 통과한 공간에서 나온 결과"임을 명시

## 7. 에이전트 시뮬레이션

### 7.1 입력
- 공간, 사물 목록, 위치: **JSON 텍스트** (관찰력을 재지 않으므로)
- NPC 대화, 문제 텍스트, 글자 수, 열린 힌트, 남은 시도 횟수: 텍스트
- 퍼즐 그림: **이미지 직접 입력** (그림 자체가 단서라 묘사하면 단서가 바뀜)
- 사물 사진: `view`한 직후 **첫 번째 사진 1장만 이미지로 입력**. 대화 기록에는 쌓지 않음
- 그림과 사진은 Files API로 한 번 올리고 실행마다 재사용, SHA-256 캐시 적용

### 7.2 페르소나 (무작위 생성)
| 속성 | 예시 |
|---|---|
| 나이 | 10대~70대 (넓게 뽑기) |
| 직업 | 학생, 약사, 개발자 ... |
| 어휘 수준 | 상 / 중 / 하 |
| 사고 방식 | 문자 그대로 읽음 / 말장난을 먼저 떠올림 / 연상을 따라감 (이 3개로 고정) |

- 실행마다 뽑힌 속성을 로그에 모두 기록
- 속성별 분석을 위해 **15회 이상** 실행 (초기 결정 "고정 3명 × 3~5회"에서 무작위로 확장)
- 선택: 데모 설명용 대표 페르소나 3명은 이름을 붙여 고정
- 실행 후 20~30대 개발 공부 중인 페르소나만 골라 오프라인 결과와 비교 가능
- 한계 명시: 어휘 제한 등은 프롬프트로만 걸리므로 모델이 어길 수 있음. 보고서에 한계로 기록
- 시간이 남으면 페르소나 속성 추가

### 7.3 진행 규칙
- 행동 목록은 로직으로 정의 (이동, 사물 찍기, 답 입력)
- **도착**: 현재 퍼즐 사물의 같은 칸 또는 이웃 칸에서 그 사물을 찍으면 NPC 대화와 퍼즐이 열림
- **시도**: 퍼즐당 5회 고정. 힌트 여부와 관계없음. 별도의 포기 행동은 없고, 5회 소진을 사람이 포기하는 지점으로 본다 (창작자의 경험에 따른 기준)
- **힌트**: 오답 수가 힌트의 `after_wrong`에 닿으면 엔진이 자동으로 텍스트 힌트 1개를 제공 (에이전트의 행동이 아님)
- **5회 소진**: 정답을 공개하고 다음 장소 지시를 받아 진행, 기록은 `failed`
- **안전 상한**: 실행당 행동 50번 (측정 지표 아님, 무한 루프 방지)

### 7.4 정답 판정 (코드)
- 입력을 소문자로 변환, 앞뒤 공백 제거 후 **정확히 일치**
- 정답 여부는 모델이 아니라 상태 머신이 판정
- 존재하지 않는 사물 선택 등은 코드가 거절하고 이유를 돌려줌

## 8. 행동 로그

```json
{
  "run_id": "r07",
  "persona": { "age": 54, "job": "약사", "vocab": "중", "thinking": "문자 그대로 읽음" },
  "puzzle_set_id": "sample-set",
  "model": "muse-spark-1.3",
  "events": [
    { "t": 1, "puzzle": 2, "type": "npc_dialogue", "npc": "librarian" },
    { "t": 2, "puzzle": 2, "type": "answer_submitted", "value": "apple", "attempt": 1, "correct": false,
      "reason": "그림에 빨간 과일이 있어서" },
    { "t": 3, "puzzle": 2, "type": "hint_revealed", "level": 1 },
    { "t": 4, "puzzle": 2, "type": "answer_submitted", "value": "pear", "attempt": 2, "correct": false,
      "reason": "과일 이름 중 짧은 것부터 시도" },
    { "t": 5, "puzzle": 2, "type": "answer_submitted", "value": "pineapple", "attempt": 3, "correct": true,
      "reason": "힌트의 '소나무'를 보고 pine을 붙임" },
    { "t": 6, "puzzle": 2, "type": "puzzle_ended", "result": "solved_with_hint", "attempts_used": 3 },
    { "t": 7, "puzzle": 2, "type": "end", "outcome": "completed" }
  ]
}
```

(위 예시는 형식을 보여 주려고 앞부분 이벤트를 생략했다. 형식의 기준은 `docs/schemas/log.schema.json`이다.)

- `reason`: 답마다 이유를 남김. 사람 테스터는 주지 않는 정보로, 오답이 "어휘를 몰라서"인지 "연결을 못 떠올려서"인지 구분하는 근거
- `correct`: 상태 머신이 채움
- 이벤트 종류: `move`, `view`, `npc_dialogue`, `answer_submitted`, `hint_revealed`, `puzzle_ended`(`result`: `solved_by_dialogue` / `solved_with_hint` / `failed`), `rejected`(코드가 거절한 행동. 점수에 넣지 않음), `end`(`outcome`: `completed` / `action_limit` / `api_error`)

## 9. 난이도 점수

실행마다 퍼즐별 점수:
- 해결: 오답 수 (0~4)
- 실패(5회 소진): **5**

집계:
- **평균 점수** = 난이도
- **실패율**, **힌트 사용률**(힌트가 열린 비율)을 함께 표시
- 평균이 같아도 "고르게 어려운 문제"와 "갈리는 문제(절반은 바로 풀고 절반은 실패)"를 구분. 갈리는 문제가 지식의 저주의 신호
- 이동, 시간, 대화 속 단서는 점수에 넣지 않음
- 실행이 중간에 끊겨 `puzzle_ended`가 없는 퍼즐은 집계에서 빼고 건수만 표시

## 10. 보고서

1. **퍼즐별 난이도 표**: 평균 점수, 실패율, 힌트 사용률
2. **갈리는 문제 분석**: 실패한 쪽과 바로 푼 쪽의 속성 비교 (예: "50대 이상, 문자 그대로 읽는 성향에서 실패율 높음")
3. **자주 나온 오답과 이유**: 퍼즐마다 상위 오답과 대표 `reason`. 창작자의 수정 단서
4. **오프라인 사례 확인**: 실제로 사람들이 막혔던 퍼즐에서 에이전트도 막혔는가. 오프라인 기록은 관찰 메모뿐이므로 수치 비교 없이 사례만 확인한다
5. **지도 화면**: 장소별 원의 크기 = 평균 점수, 색 = 실패율. 에이전트 발자국(고스트) 재생
6. **한계**: 페르소나 준수의 한계, 비교 퍼즐 수의 한계, 속성값별 표본 수의 한계 (15회 실행이면 사고 방식 값별 약 5회), 사진을 잘못 봐서 틀린 경우가 섞일 수 있는 한계

주장의 범위: 통계적으로 "사람을 닮았다"가 아니라, **에이전트 시뮬레이션으로 난이도를 추정하고, 사람이 막혔던 퍼즐에서 에이전트도 막히는지 사례로 확인**한다.

### 10.1 저주 지수 (여유)
- 제작자가 첫 실행 전에 퍼즐별 예상 점수를 적고, 보고서가 실제 평균 점수와의 차이를 보여 준다
- 지식의 저주를 숫자로 보여 주는 지표. 결과를 본 뒤에 적으면 의미가 없으므로 첫 실행 전에 고정한다

### 10.2 수정과 재검증 (여유)
- 폐루프: Muse가 대화나 힌트의 수정안을 제안 → 제작자가 선택 → 다시 실행 → 전후 비교
- 기준은 쉬워졌는지가 아니라 제작자의 예상 점수에 가까워졌는지
- 표본이 적으므로 개선의 증명이 아니라 사례로 보고한다
