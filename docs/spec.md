# Real-to-Sim 공간 퍼즐 스튜디오 — 명세 v1.1

> Meta Global AI Developer Hackathon 출품작 · 브레인스토밍 결과 정리 (2026-11-03) · 코드 폴더 위치: `docs/spec.md`

## 1. 한 줄 정의

공간형 퍼즐을 설치하기 전에, 서로 다른 성향의 AI 에이전트들이 시뮬레이션 안에서 먼저 플레이해 보고 **퍼즐이 제작자의 머릿속에만 갇혀 있지 않은지(지식의 저주)** 를 검증하는 도구.

로봇에서 MuJoCo로 실물 전에 동작을 돌려 보듯, 공간 퍼즐에도 "만들기 전에 돌려 보는 단계"를 만든다.

## 3. 측정 대상과 범위

**측정하는 것**
- 퍼즐의 연결이 제작자 아닌 사람에게도 떠오르는가 (문제 난이도의 적절성)

**측정하지 않는 것**
- 장소 이동, 길찾기 (지시문으로 장소를 분명히 정의함. 쉬워져도 무방)
- 관찰력 (사물을 찾아내는 능력)

**이번 범위 밖 (Non-goals)**
- AR 기능 (원작은 리얼월드 스튜디오 AR 사용. 시뮬레이션에서는 "사물을 본다"로 추상화)
- 3D 복원 (MapAnything 등). 평면도로 충분
- 온라인 사람 테스트 수집. 사람 기준 데이터는 오프라인 기록을 사용
- 게임 모드 (플레이 중 고스트 표시)
- 30분 분량 전체 이식. 핵심 퍼즐만 이식

## 4. 전체 구조와 착수 순서

```
[1단] 공간 재연 ──▶ [재연 검증] ──▶ [에이전트 시뮬레이션] ──▶ [로그] ──▶ [보고서]
```

에이전트는 공간을 JSON으로 받고 이동을 측정하지 않으므로, 두 갈래를 나란히 진행한다.

| 갈래 | 내용 | 순서 |
|---|---|---|
| 갈래 1 (핵심) | 퍼즐 JSON → 에이전트 실행 → 로그 → 보고서 | 먼저 |
| 갈래 2 (보여 주기) | 평면도, 격자, 발자국 지도, 주문 연출 | 뒤에 합류 |

로그 형식을 먼저 확정하면 두 갈래가 서로를 기다리지 않는다. 지도가 덜 되어도 보고서가 있으면 결과물이 성립한다.

## 5. 1단: 공간 재연

### 5.1 평면도
- 창작자가 마우스로 공간 형태를 그림 (벽, 문)
- 그리기 배경으로 비상대피도 사진 사용 가능 (비율이 맞는 기준 1장)

### 5.2 축척
- 그린 문의 픽셀 폭을 **0.9m** 로 간주해 자동 계산. 창작자의 직접 측정 없음
- 문이 여러 개면 평균, 배율 차이가 크면 경고

### 5.3 격자 좌표 (체스식)
- 열은 알파벳, 행은 숫자. **왼쪽 아래가 A1**. 26열 초과 시 AA, AB...
- **칸 크기 1m**
- 원점은 평면도 바깥 사각형의 왼쪽 아래
- 층이 여러 개면 접두어: `2F-C4`
- 같은 사물도 좌표로 구분: `desk@C4`, `desk@F2`
- 큰 사물이나 구역은 범위: `B3:D5`

### 5.4 사물
```json
{
  "id": "desk@C4",
  "label": "desk",
  "cells": "C4:D4",
  "description": "",
  "photos": ["desk_front.jpg", "desk_puzzle.jpg"],
  "state": "locked"
}
```
- 트리거: 같은 칸 또는 이웃 칸에 들어오면 사진이 열림
- 사물 라벨과 칸 위치는 SAM 3.1(박스) + Muse Spark(이름, 대략적 크기)가 사진에서 제안하고 창작자가 배치
- 크기 추정 방식은 미결 (§12): SAM 박스 비율(같은 사진 속 문 기준) 또는 Muse 추정

### 5.5 퍼즐
- **선형 구조**: 1번을 풀면 다음 장소 지시를 받음
- 지시문에 좌표를 포함해도 됨 (예: "C4의 책상으로 가라")
- 퍼즐 정보: 그림 이미지, 문제 텍스트, 정답 단어 개수, 텍스트 힌트 1개

## 6. 재연 검증

원칙: AI가 만든 결과를 **AI 밖의 코드로 검증**하고, 실패하면 이유를 돌려주어 다시 만들게 한다 (워크숍 구조).

### 6.1 자동 검사 (필수)
| 대상 | 검사 |
|---|---|
| 평면도 | 벽이 닫혀 있는가, 문이 벽 위에 있는가 |
| 축척 | 문 폭 기준 배율끼리 크게 어긋나지 않는가 |
| 사물 | 방 안에 있는가, 서로 겹치지 않는가, 크기가 상식 범위인가 (책상 0.6~2m 등) |
| 트리거 | 퍼즐에 쓰이는 사물마다 사진이 있는가 |
| 연결 | 지시문이 가리키는 사물이 지도에 있는가, 길이 있는가 |

### 6.2 오라클 실행 (필수)
- 모든 정답을 아는 가짜 플레이어가 1번부터 끝까지 진행
- 끝까지 가면 플레이 가능한 시뮬레이션. 막히면 퍼즐이 아니라 재연의 문제

### 6.3 내용 동일성
- 퍼즐 이미지, 문제 텍스트, 단어 개수, 힌트가 오프라인과 같은가
- 사물 설명(JSON)이 원래 없던 단서를 흘리지 않는가 (제작자가 무의식적으로 답 쪽으로 기운 설명을 쓰는 것 방지)

### 6.4 출력
- 재연 보고서: 통과 항목, 수정 항목, 창작자 확인 필요 항목
- 최종 보고서에 "재연 검증을 통과한 공간에서 나온 결과"임을 명시

## 7. 에이전트 시뮬레이션

### 7.1 입력
- 공간, 사물 목록, 위치: **JSON 텍스트** (관찰력을 재지 않으므로)
- 문제 텍스트, 단어 개수, 힌트: 텍스트
- 퍼즐 그림: **이미지 직접 입력** (그림 자체가 단서라 묘사하면 단서가 바뀜)
- 그림은 Files API로 한 번 올리고 실행마다 재사용, SHA-256 캐시 적용

### 7.2 페르소나 (무작위 생성)
| 속성 | 예시 |
|---|---|
| 나이 | 10대~70대 (넓게 뽑기) |
| 직업 | 학생, 약사, 개발자 ... |
| 어휘 수준 | 상 / 중 / 하 |
| 사고 방식 | 문자 그대로 읽음 / 말장난을 먼저 떠올림 ... |
| 힌트 시점 | 오답 2번 / 3번 / 4번 후 힌트 확인 |

- 실행마다 뽑힌 속성을 로그에 모두 기록
- 속성별 분석을 위해 **15회 이상** 실행 (초기 결정 "고정 3명 × 3~5회"에서 무작위로 확장)
- 선택: 데모 설명용 대표 페르소나 3명은 이름을 붙여 고정
- 실행 후 20~30대 개발 공부 중인 페르소나만 골라 오프라인 결과와 비교 가능
- 한계 명시: 어휘 제한 등은 프롬프트로만 걸리므로 모델이 어길 수 있음. 보고서에 한계로 기록
- 시간이 남으면 페르소나 속성 추가

### 7.3 진행 규칙
- 행동 목록은 로직으로 정의 (예: 이동, 사진 보기, 답 입력, 힌트 보기)
- **힌트**: 페르소나의 힌트 시점에 도달하면 텍스트 힌트 1개 확인
- **포기**: 한 퍼즐에서 오답 5번 → 정답과 다음 장소 지시를 받고 진행, 기록은 "도움 받음" (오프라인에서 운영자가 직접 도와준 것에 대응)
- **안전 상한**: 실행당 행동 50번 (측정 지표 아님, 무한 루프 방지)

### 7.4 정답 판정 (코드)
- 입력을 소문자로 변환, 앞뒤 공백 제거 후 **정확히 일치**
- 정답 여부는 모델이 아니라 상태 머신이 판정
- 존재하지 않는 사물 선택 등은 코드가 거절하고 이유를 돌려줌

## 8. 행동 로그

```json
{
  "run_id": "r07",
  "persona": { "age": 54, "job": "약사", "vocab": "중", "thinking": "문자 그대로", "hint_after": 3 },
  "events": [
    { "t": 1, "puzzle": 2, "type": "answer", "value": "apple", "correct": false,
      "reason": "그림에 빨간 과일이 있어서" },
    { "t": 2, "puzzle": 2, "type": "hint" },
    { "t": 3, "puzzle": 2, "type": "answer", "value": "pineapple", "correct": true,
      "reason": "힌트의 '소나무'를 보고 pine을 붙임" }
  ]
}
```

- `reason`: 답마다 이유를 남김. 사람 테스터는 주지 않는 정보로, 오답이 "어휘를 몰라서"인지 "연결을 못 떠올려서"인지 구분하는 근거
- `correct`: 상태 머신이 채움
- 이벤트 종류: `move`, `view`, `answer`, `hint`, `assisted`(포기 후 도움), `end`

## 9. 난이도 점수

실행마다 퍼즐별 점수:
- 오답 수 (0~4)
- 힌트를 봤으면 +1
- 포기(오답 5번)면 최댓값 **6**

집계:
- **평균 점수** = 난이도
- **포기율**, **힌트 사용률**을 함께 표시
- 평균이 같아도 "고르게 어려운 문제"와 "갈리는 문제(절반은 바로 풀고 절반은 포기)"를 구분. 갈리는 문제가 지식의 저주의 신호
- 이동, 시간은 점수에 넣지 않음

## 10. 보고서

1. **퍼즐별 난이도 표**: 평균 점수, 포기율, 힌트 사용률
2. **갈리는 문제 분석**: 포기한 쪽과 바로 푼 쪽의 속성 비교 (예: "50대 이상, 문자 그대로 읽는 성향에서 포기율 높음")
3. **자주 나온 오답과 이유**: 퍼즐마다 상위 오답과 대표 `reason`. 창작자의 수정 단서
4. **오프라인 사례 확인**: 실제로 사람들이 막혔던 퍼즐에서 에이전트도 막혔는가
5. **지도 화면**: 장소별 원의 크기 = 평균 점수, 색 = 포기율. 에이전트 발자국(고스트) 재생
6. **한계**: 페르소나 준수의 한계, 비교 퍼즐 수의 한계

주장의 범위: 통계적으로 "사람을 닮았다"가 아니라, **에이전트 시뮬레이션으로 난이도를 추정하고, 사람이 막혔던 퍼즐에서 에이전트도 막히는지 사례로 확인**한다.

## 11. 화면과 연출

### 11.1 컨셉
- 이야기의 축: 『은하수를 여행하는 히치하이커를 위한 안내서』 오마주 → "이 공간의 안내서"
- 기술의 축: Meta 모델

| 요소 | 쓰임 |
|---|---|
| **Don't Panic** | 여는 주문 |
| **Segment Anything** | 열리는 순간 사물이 윤곽선과 함께 떠오르는 연출 (SAM 결과 표시) |
| **So long, and thanks for all the fish** | 닫는 주문. 발자국이 스며들 듯 사라지고 안내서 페이지(보고서)가 남음 |
| Babel fish | 자유 문장 해석 모듈 이름 |
| Deep Thought | 에이전트 테스터 이름 |
| Mostly Harmless | 보고서 판정 등급 |

- 42는 사용하지 않음
- 여닫는 문장은 창작자가 정할 수 있는 기능, 위 문구는 42경산 데모의 기본값
- 여는 주문 판정: 1단계는 정확한 문장 일치, 이후 Muse Spark 의도 해석으로 교체 가능

### 11.2 지도 표현
- 모티프: 해리포터의 마루더즈 맵(Marauder's Map) — 주문으로 열고 닫는 지도, 이름표 달린 발자국으로 이동 표시
- 평면도 위 텍스트와 도형, 가장자리에 격자 좌표 표기
- 층은 접힌 종이 면으로 전환 (시간이 남으면)
- 사진 처리 중 잉크가 번지며 그려지는 연출 (시간이 남으면)

### 11.3 고스트
- 에이전트들은 각자 독립된 상태에서 따로 실행
- 기록을 시간축에 맞춰 같은 지도에 재생해 동시에 움직이는 것처럼 표시
- 실시간 실행이 아니라 미리 실행한 기록의 재생

## 12. 보류 및 미결 사항

| 항목 | 상태 |
|---|---|
| 퍼즐 선정 | 구현 단계에서 확정. 기준: 사람이 막힌 퍼즐 1~2개 + 쉽게 푼 퍼즐 1~2개, 공간이 서로 이어질 것 |
| 사진 재촬영 | Modal로 SAM을 돌려 보며 판단 |
| 가구 크기 추정 | SAM 박스 비율 vs Muse 추정, 둘 다 시도 후 결정 |
| 여닫는 주문의 주체 | 사람 플레이를 범위에서 뺐으므로, 주문 의식을 누가 하는지(보고서 열람 의식 등) 정리 필요. Babel fish(행동 해석) 역할도 이에 따라 재정의 |
| 오답 피드백 | 오답일 때 에이전트에게 무엇을 알려 줄지. 오프라인과 같게 |
| 퍼즐 간 기억 | 에이전트가 한 실행 안에서 이전 퍼즐 경험을 기억하는지 |
| 보고서 분담 | 제안: 점수와 비율은 코드, 오답 이유 요약만 Muse |
| 프론트 기술 스택 | 지도 렌더링(SVG/캔버스), 프레임워크 여부. Pannellum은 불필요할 수 있음 |
| 마감 시각 | 11/4 한국 시간, 정확한 시각 확인 |
| 제출물 | 데모 영상(핵심 퀴즈만), README, 배포 여부. 해커톤 규정 확인 후 결정 |

- 워크숍 코드: README에 `meta-models/legal-agent-workshop` 출처 명시. 저장소 루트에 LICENSE가 보이지 않으므로 해커톤 규정의 기존 코드 사용 조건 확인
- 오프라인 퍼즐 에셋: 리얼월드 스튜디오 플랫폼 제공 에셋이 섞여 있다면 이용약관 확인
- 해커톤 규정의 제3자 IP 조항 확인

## 14. 구현 문서 구성

이 파일(`docs/spec.md`)이 요구사항과 결정 기록을 맡는다. 구현 전에 아래 문서를 추가로 작성한다.

| 문서 | 형식 | 담을 내용 |
|---|---|---|
| `docs/design.md` | md | 아키텍처(공간 빌더, 검증기, 게임 엔진, 페르소나 생성기, 에이전트 실행기, 로그 저장소, 보고서 생성기, 뷰어 / 외부 의존: Muse Spark API, Modal 위 SAM 3.1, Files API), 폴더 구조(워크숍 `agent/` 파일 위치 포함), 인터페이스 계약(게임 엔진 입출력, 에이전트 관측과 출력 `action`/`value`/`reason`, 형식 오류와 API 실패 처리), 상태 전이표, 규칙(정답 판정, 힌트와 포기, 점수, 페르소나 생성), 보고서 분담, 미결 TODO |
| `docs/schemas/` | `.schema.json` | `space`, `puzzle`, `persona`, `log`, `baseline`(오프라인 기록). 코드가 이 파일로 데이터를 검증 |
| `docs/acceptance.md` | md | 검사 가능한 문장으로 쓴 완료 기준 (오라클 실행 통과, 데이터가 스키마 만족, 무작위 페르소나 15회 이상, 보고서 생성, 고스트 재생 등). 필수와 여유 시 항목 구분 |
| `README.md` | md | 설치, `.env`, 실행 명령, 출처 표기, Muse Code로 구현했다는 점 |

작성 순서: `schemas/` → `design.md`의 인터페이스 계약 → `acceptance.md` → `design.md` 나머지 → `README.md`

확인할 것: Muse Code가 프로젝트 지침 파일을 자동으로 읽는지. 읽는다면 그 파일에서 위 문서들을 가리키고, 아니면 작업마다 참조 문서를 직접 지정한다.
