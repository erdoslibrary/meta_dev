# 구현 문서 구성

Nov 3, 2026 · @수목원

워크숍 코드 폴더에서 Muse Code로 구현하려면 문서 5종이 필요합니다. 스키마와 인터페이스 계약을 가장 단단하게 쓰면, 나머지는 Muse Code에게 "이 스키마와 계약을 만족하고 수용 기준을 통과하도록 구현하라"고 맡길 수 있습니다. 요구사항은 기존 `realtosim_spec.md`가 이미 맡고 있습니다.

## 필요한 문서

| 문서 | 형식 | 담을 내용 |
| --- | --- | --- |
| `spec.md` | md (기존 파일) | 요구사항, 범위, 비목표, 결정 기록. `realtosim_spec.md`를 그대로 옮김 |
| `design.md` | md | 아키텍처(구성 요소, 데이터 흐름, 외부 의존), 폴더 구조, 인터페이스 계약, 상태 전이표, 규칙(정답 판정, 힌트와 포기, 점수, 페르소나 생성), 보고서에서 코드와 모델의 분담 |
| `schemas/` | `.schema.json` | `space`, `puzzle`, `persona`, `log`, `baseline`(오프라인 기록) |
| `acceptance.md` | md | 검사 가능한 문장으로 쓴 완료 기준. 필수와 여유 시 항목을 나눔 |
| `README.md` | md | 설치, `.env`, 실행 명령, 출처 표기, Muse Code로 구현했다는 점 |

`design.md`의 각 부분에 들어갈 세부 항목입니다.

- **아키텍처:** 공간 빌더, 검증기, 게임 엔진, 페르소나 생성기, 에이전트 실행기, 로그 저장소, 보고서 생성기, 뷰어. 외부 의존은 Muse Spark API, Modal 위 SAM 3.1, Files API
- **폴더 구조:** 워크숍 `agent/`에서 가져온 파일의 위치 포함
- **인터페이스 계약:** 게임 엔진 함수의 입출력, 에이전트 관측 형식과 출력 형식(`action`, `value`, `reason`), 형식 오류와 API 실패 처리
- **상태 전이표:** 퍼즐 상태(잠김 → 진행 중 → 힌트 봄 → 해결 / 도움 받음)와 실행 상태
- **미결 TODO:** 오답 때 주는 피드백, 퍼즐 간 기억 여부, 프론트 스택, 가구 크기 추정 방식, 주문 의식의 주체

`schemas/`는 md가 아니라 실제 JSON Schema 파일로 둡니다. 코드가 이 파일로 데이터를 검증할 수 있어, "AI 결과를 코드로 검증한다"는 원칙이 스키마 단계부터 성립합니다.

## 작성 순서

뒤 문서가 앞 문서에 기대므로 이 순서로 씁니다.

1. `schemas/`: 구성 요소를 잇는 유일한 약속
2. `design.md`의 인터페이스 계약: 갈래 1(에이전트, 로그, 보고서)과 갈래 2(지도, 연출), 테스트가 모두 의존하는 고정점
3. `acceptance.md`: 시간이 모자랄 때 무엇을 자를지 정하는 기준
4. `design.md`의 나머지: 아키텍처, 상태 전이, 규칙, 보고서 분담
5. `README.md`

열린 질문: Muse Code가 `CLAUDE.md`처럼 프로젝트 지침 파일을 자동으로 읽는지 확인 필요. 읽는다면 그 파일에서 위 문서들을 가리키고, 아니면 작업마다 참조 문서를 직접 지정합니다.
